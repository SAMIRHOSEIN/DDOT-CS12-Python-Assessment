# DDOT CS-12 Data Scientist | Python Assessment

**Project:** 2026 utility permit locations and FHWA roadway functional classification  
**Study area:** District of Columbia  
**Unit of final delivery:** one row per TOPS `LocationID`, retaining its `TrackingNumber` and the application-level highest FHWA functional class when fully verified.

## 1. Objective and scope

This reproducible Python workflow:

1. Inspects the TOPS permit data schema and exploratory samples.
2. Downloads TOPS locations for **Construction Staging Area** or **Mobile Crane Work Zone** permits with an **ApplicationDate OR IssueDate in calendar year 2026**.
3. Identifies the applicants **DC Water, PEPCO, and Washington Gas**.
4. Filters and checks permit IDs, applicants, activity types, and dates.
5. Assesses spatial fields, the candidate coordinate reference system (CRS), and Original versus OnSeg coordinates.
6. Uses the DDOT roadway linear referencing service (LRS) to identify potential roadway `SubBlockKey` values, then the official Roadway SubBlock layer to retrieve `FHWAFUNCTIONALCLASS` and check the roadway identity.
7. Aggregates verified location classes by `TrackingNumber` to find the **highest functional class**, and joins the application result back to every location.

**Important distinction:** a `TrackingNumber` identifies an application, while a `LocationID` identifies a location associated with that application. Several locations can share a `TrackingNumber`. `SubBlockKey` identifies a roadway segment in DDOT roadway data; it is not the permit location ID.

From the project root in **Windows PowerShell**:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

On macOS/Linux, replace the first two lines with `python3 -m venv .venv` and `source .venv/bin/activate`.

The scripts can be executed from a terminal. They also contain `# %%` markers for running cells in the VS Code Python Interactive window; the optional `ipykernel` dependency is included in `requirements.txt` for this workflow.

## 4. How to run each step

Run the scripts from the repository root, in the following order:

```powershell
python src/01_explore_data.py
python src/02_download_permits.py
python src/03_identify_utility_companies.py
python src/04_validate_and_filter_permits.py
python src/05_spatial_assessment_and_pilot.py
```

- **Step 01** reads the two existing exploratory JSON files under `data/samples/`; it does **not** download them.
- **Step 02** queries ArcGIS TOPS using object IDs and verifies every 500-ID batch against the requested IDs. It saves `data/raw/permits_2026_applied_or_issued_staging_crane_all_companies.json`. Re-running it may update the snapshot and therefore later counts.
- **Step 03** explores applicant-related name fields to discover company-name variants. It is an exploratory/console-report script, not the final filtering step.
- **Step 04** uses the confirmed `ApplicantCompany` mapping, checks related `PermitteeName`/`OwnerName` evidence, validates identifiers and filters, writes QA files to `outputs/validation/`, and saves `data/processed/permits_2026_applied_or_issued_staging_crane_three_utilities.json`.
- **Step 05** checks coordinates and tests nearby road candidates on a small pilot. Its `outputs/spatial/` files are QA artifacts; it does **not** assign final classes.

### Step 06: roadway identity and FHWA functional class

In `src/06_match_roadways_and_assign_functional_class.py`, use:

```python
RUN_MODE = 'pilot'   # first test: 18 locations
# RUN_MODE = 'full'  # subsequent full run: 4,926 locations
```

Then execute:

```powershell
python src/06_match_roadways_and_assign_functional_class.py
```

The pilot selects up to **three locations per (utility company × Original/OnSeg coordinate group)**. It is a deterministic functional check, **not** a statistically representative accuracy sample. For the full run, change to `RUN_MODE = 'full'` and execute the same command again.

How matching works:

1. Use OnSeg once when Original and OnSeg are numerically identical. When they differ, evaluate **both** coordinate sources; do not reject differences by a displacement threshold.
2. Query candidate subblocks through the LRS using **75 m**, extending to **200 m** when needed. These radii are **candidate-discovery windows**, not proof of the correct road.
3. Look up each candidate `SubBlockKey` in the official Roadway SubBlock layer to obtain roadway name, road type and functional class.
4. Check normalized street name/quadrant, complete numeric address range, roadway type, nearest-road evidence, and class consistency. Handle the documented Capitol Street suffix aliases and supported two-road intersection addresses conservatively.
5. If several acceptable subblocks agree on class, a class can be verified without inventing a unique `SubBlockKey`. If the evidence conflicts or is insufficient, retain the row as `PROVISIONAL` or `UNRESOLVED` with a reason.

Outputs are placed under `outputs/roadway_functional_class/{pilot|full}/`:

| CSV | Purpose |
|---|---|
| `permit_locations_fhwa_functional_class.csv` | **Primary Step 06 output**, one row per TOPS `LocationID` with the matched class/status |
| `permit_locations_lrs_roadway_candidate_evidence.csv` | All evaluated LRS/official-subblock candidate evidence, including alternative keys |
| `permit_locations_functional_class_needing_review.csv` | Unverified locations, `MatchStatus`, explanation, and `SuggestedNextAction` (suggested, **not implemented**) |
| `permit_locations_api_errors.csv` | Request/processing errors, if any |
| `roadway_matching_status_summary.csv` | Counts and percentages for each matching status |

Raw API response caching: `outputs/roadway_functional_class/ddot_lrs_raw_api_cache.sqlite3`. This database stores **responses**, not final classification decisions. It can prevent duplicate network requests, but deleting it means rerunning the relevant API calls.

**Checkpoint warning:** Step 06 skips already completed `LocationID` values within an existing mode's CSV. If you **change the matching rules or source data**, back up/rename that mode's CSV output directory before a clean recalculation. Otherwise old decisions may be reused. You can keep the raw API cache when the underlying responses remain valid. Close open CSV files in Excel before overwriting them on Windows.

### Step 07: highest functional class by application

In `src/07_calculate_highest_functional_class_per_permit.py`, set the **same mode** as Step 06 (`pilot` or `full`) and run:

```powershell
python src/07_calculate_highest_functional_class_per_permit.py
```

The program groups `LocationID` rows by `TrackingNumber`. **Among fully verified applications**, the highest functional class corresponds to the **lowest numerical FHWA class code**, so `min()` is appropriate (e.g. Class 3 ranks above Class 5). Only `ClassStatus='VERIFIED'` is final evidence; provisional classes are never silently promoted.

If **any location within a TrackingNumber is unverified**, `HighestFHWAFunctionalClassPerPermit` remains **blank**. The code may show `HighestFHWAClassAmongVerifiedLocations` for context, but this is **not the confirmed highest class for the whole application**. Its reasons and affected locations remain available for follow-up.

Two primary deliverables are saved under:

`outputs/permit_highest_functional_class/01_primary_results/{pilot|full}/`

`outputs/permit_highest_functional_class/02_quality_control_and_limitations/{pilot|full}/`

## 6. Validation already performed and recommended extensions

**Implemented checks:** batched download ID completeness, no duplicate `LocationID`, date/activity checks, applicant mapping and ID relationship review, spatial QA, official roadway-attribute consistency, matching evidence retained, output reconciliation, and application-level aggregation checks. Step 07's confirmed minimum-class results can also be independently reproduced with Pandas `groupby`.

**Not implemented in this archived submission:** a statistically independent GIS/manual ground-truth audit, a separate MAR verification pass, formally confirmed CRS metadata for TOPS Original/OnSeg, and a dedicated automated `tests/` suite. These are possible extensions, not completed validation claims. The candidate TOPS local CRS is **EPSG:26985**, compared with source ArcGIS geometry **EPSG:3857**; their positional agreement supports the working interpretation but is not an official CRS certification.

**Nearest-road distance comparison:** parts of Step 06 use exact equality (`==`) of LRS offsets to identify nearest-road ties. A tolerance-based `math.isclose()` experiment has **not** been applied to the archived classification results. A near-tie may reveal ambiguity rather than create more verified records. Also, exact Original/OnSeg inequality is a **separate** deliberately conservative rule: any numerical difference causes both points to be evaluated.

## 7. Reproducibility and limitations

- The outputs are tied to the source snapshot above. Record counts may change if Step 02 fetches live TOPS data again.
- Raw responses saved in SQLite accelerate reruns. Back up or clear old **classification CSVs** when changing classification logic.
- The pipeline does **not** silently exclude unverified locations, fabricate functional classes, or resolve ambiguous bridge/ramp/intersection locations using guesses.
- The dataset and output folders are listed in the existing `.gitignore`. To distribute a **complete reproducible submission**, package the relevant `data/` and `outputs/` files explicitly if permitted, rather than assuming Git tracked them. Do **not** needlessly include `.git/` or large caches in a submission archive.
- Dependencies in `requirements.txt` are **compatible version ranges**, not an exact record of the original Windows environment. To archive exact installed package versions, use `python -m pip freeze > environment_freeze.txt` after running in the final environment.
- The workflow uses public DDOT/DCGIS ArcGIS services; availability and response content are not controlled by this project.

## 8. Troubleshooting

| Symptom | Check |
|---|---|
| `FileNotFoundError` | Run from the project root; ensure `data/samples/` and required upstream JSON/CSV files exist |
| Missing package (`ModuleNotFoundError`) | Activate `.venv` and run `python -m pip install -r requirements.txt` |
| ArcGIS/DDOT API error | Check internet/service access; retry; Step 06 can resume from checkpoints |
| Script appears to finish without redoing Step 06 | This is checkpoint behavior; remove/rename the mode's saved classification CSVs only when a clean recomputation is intended |
| `PermissionError` replacing a CSV | Close the CSV in Excel, then rerun |
| Step 07 reports missing Step 06 results | Run Step 06 using the same `pilot` or `full` setting first |
| Many review cases remain | Inspect the review CSV and candidate evidence; do not replace unknown results with the nearest class without evidence |
